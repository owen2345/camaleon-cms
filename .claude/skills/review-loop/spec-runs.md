# Spec runs and failed checks

The spec runs of the loop, the openspec commands, the failed checks and the fixup commit of a failure fix follow this file (`procedure.md`, Checks).

- A spec run before a commit runs the specs of the fix, the adjacent specs and the spec files of the branch (`docs/ai/workflows.md` Phase 3). It never runs the whole suite. The exceptions are a trace (`trace.md`) and an adjacent set of more than half of the suite (`AGENTS.md`). `docs/ai/testing.md` says which files `bin/rspec` gets. A commit with no such spec file skips the run, and rspec is n/a. A commit that touches `openspec/` also runs the `openspec validate` commands of `AGENTS.md`.
- A failed check follows `docs/ai/failures.md` for its cause and Phase 3 for its fix. For a spec run, the spec clone takes the place of the checkout, except for a host app (below). The ignored file of step 3 is then a file of the spec clone. The clone of step 1 is a clone of its own, made only when step 3 runs. The run of step 2 without the fix comes first, in the spec clone synced with `no copy`, and its `task` line ends with `# no fix`.
- A failure whose cause `docs/ai/failures.md` does not find stops the run: report the check with its log. A check that fails at the start commit of the branch in the same way (step 4) stops the run too. Leave the uncommitted fix in the tree, and name it in the report as the run's own.
- When a commit of the branch caused the failure, make its fixup commit as Phase 3 says. The loop skips the rebase (`procedure.md`, Ledger rows). The FIXED row of the failure fix names the fixed commit after its fix SHA, `<sha> fixes <sha>`. Its `fix` line ends with one more field, that SHA. A fixup commit stops the run after the last commit of the pass (`procedure.md`, Pass states and stop).
- The fixup command (Phase 3) takes two trees. `<before>` is the `<tree>` of the batch before the failure fix, or HEAD with no uncommitted fix. `<after>` is the `<tree>` of the first batch after the failure fix, or after its repair. When the uncommitted fix changed between the two, the two fixes share one commit, as after an apply that exits with 1.
- A spec run of the loop, before a commit or in a trace, runs in the spec clone, `<scratchpad>/<repo>-clone`, never in the checkout. A host app is the exception (below). Sync the spec clone before the run, with the ten-minute timeout. Start with `set -o pipefail;`, then join these parts with `&&` in this order. A run names `<commit>` and the parts that it skips, and a failed sync has no result (`procedure.md`, Checks).
  - The clone, when the spec clone does not exist: `[ -d <spec clone> ] || git clone -q <checkout> <spec clone>`.
  - The reset: `git -C <spec clone> fetch -q <checkout> HEAD && git -C <spec clone> reset -q --hard <commit> && git -C <spec clone> clean -fdq`, with `FETCH_HEAD` as `<commit>` unless the run names another commit. A run that names another commit fetches it too, since an older clone can lack it: `git -C <spec clone> fetch -q <checkout> HEAD <commit>`.
  - The merge, in a trace only (`trace.md`).
  - The copy of the uncommitted changes: `git -C <checkout> add -A && git -C <checkout> diff HEAD --binary | git -C <spec clone> apply --3way --allow-empty`, skipped by a run that names `no copy`.
  - The install: `(cd <spec clone> && bundle install --quiet)`.
- The spec clone keeps its caches (`git clean` without `-x`). No other spec run shares its files or its SQLite file, so a failed spec run there counts.
- A host app on PostgreSQL (camaleon_website, florsan) runs its specs in the checkout. A clone lacks the ignored files that its boot reads, and its test database is shared with every checkout anyway. A spec run there starts only when no other spec run is active, under the wait for other runs of `docs/ai/testing.md` "Which specs to run". A run still active after the hour stops the run, and the report names its pids.
- A failed spec run of a host app follows `docs/ai/failures.md` "Second run" in the checkout, and never its Bisect. A spec run that fails again in the same way stops the run: report the failed examples.
