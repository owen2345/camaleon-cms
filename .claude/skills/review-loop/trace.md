# Trace of a failed suite job

The review loop reads this file when a suite job of the PR head fails (`procedure.md`, Checks). The trace finds the cause of the failure in the spec clone, or in the clone of `docs/ai/failures.md` step 1. The loop finds the cause as that document says, and fixes it as `docs/ai/workflows.md` Phase 3 says.

- Several suite jobs can fail with the same examples. Then trace the job whose cell is that of the spec clone: its Gemfile and its Ruby. When no job has that cell, trace the first of these jobs that the jobs command of Checks lists.
- Reproduce the failed job as `docs/ai/failures.md` says, in the spec clone (`procedure.md`, Checks), from its job log. The job id of `--log-failed` is the `databaseId` that the jobs command of Checks prints. When the spec clone exists, first run `git -C <spec clone> clean -fdqx`: a fresh CI checkout has no ignored file and no old lock. Then sync the spec clone, before every run of the trace.
- The log of a job can be gone: `gh` prints `log not found`, or HTTP 410 for an expired log. That output is the result of the command, and the failure is one that the spec clone does not show (below). After the rerun that the trace started, give `--attempt <n>` to the jobs command and to the log commands (`docs/ai/failures.md`). `<n>` is one less than the number that `gh run view <run id> --repo <project> --json attempt --jq .attempt` prints.
- The job log names the base commit that CI merged (`docs/ai/failures.md`): `gh run view --repo <project> --job <job id> --log | grep -m1 -oE 'Merge [0-9a-f]+ into [0-9a-f]+' | awk '{print $4}'` prints it. When it prints nothing, the job did not merge the base: the sync then has no merge part.
- So the merge part of the sync (`procedure.md`, Checks) is `git -C <spec clone> fetch -q <checkout> refs/remotes/<base-ref> && git -C <spec clone> merge -q --no-edit <base of the job>`. The fetch brings that commit, an ancestor of the base, into the spec clone. A conflict stops the run: report it, because the branch needs a rebase onto the base. A run that reproduces the job names the head of the failed run as `<commit>`, and `no copy`. That head is the `<sha>` of the ci commands (`procedure.md`, Checks), and CI tested it without the uncommitted changes. The run after the fix syncs with `FETCH_HEAD`, the merge and the copy, so that it tests the fix.
- The clone of `docs/ai/failures.md` step 1 gets no merge: check out the head of the failed run there. The bisect inputs: `<bad>` is that head, each command gets the cell of the job, and the run that failed had no fix. In the commands that run in that clone, `<clone>` takes the place of `<spec clone>`. When the check passes there in step 3 and `git -C <spec clone> diff --quiet <head of the failed run> HEAD` exits with 1, the merge caused the failure, not an ignored file. Stop the run, and report it: the branch needs a rebase onto the base.
- Every command of the trace in the spec clone, each sync included, starts with the cell of the job: `export BUNDLE_GEMFILE=<spec clone>/gemfiles/<rails>.gemfile MISE_RUBY_VERSION=<version>;`. `<rails>` is the gemfile name of the cell, and `<version>` the Ruby minor version of the job, both from the workflow file. Leave out a variable when the workflow file gives the job no value for it. Leave out `MISE_RUBY_VERSION` also when `mise ls --installed ruby` has no Ruby of that minor version, and say so in the report (`docs/ai/failures.md`). When the workflow names `.tool-versions`, leave `MISE_RUBY_VERSION` out too: the spec clone has the same file. For a job with neither value, the trace runs on the Gemfile and the Ruby of the spec clone.
- The path of the gemfile is absolute (`docs/ai/failures.md`). With the export, the sync installs that gemfile, and its clean keeps the lock. The ban of `docs/ai/failures.md` on another gemfile applies to the checkout, not to the spec clone.
- For a spec step, run the failed examples first. When they pass alone, a flake is likely: start the one rerun of the run (`procedure.md`, Checks). Meanwhile, run the files of the job with its seed, if any, as `docs/ai/failures.md` says. For a suite job of camaleon-cms, that is the whole suite, as a background task (`procedure.md`, Checks).
- For a step that is not a spec run, run that step alone in the spec clone. Examples are `bin/rubocop` and a migration. Such a step needs no second run on the same tree (`docs/ai/failures.md`). When such a step passes in the spec clone, the failure is one that the spec clone does not show (below).
- A step that only prepares the runner does not run on this machine (`docs/ai/failures.md`). The failure of such a step is one that the spec clone does not show (below). The rerun that `docs/ai/failures.md` asks for is the one rerun of the run (`procedure.md`, Checks).
- For a host app, the checkout takes the place of the spec clone in this file, without the clean and the sync (`procedure.md`, Checks). A host-app trace runs on the current tree of the checkout. When that tree differs from the head of the failed run, the report says so.
- The trace reproduces only a spec step of a host-app job. A failed step that only prepares the runner gets the one rerun, as above. Any other failed step that is not a spec step stops the run: report it with its log. A host-app spec failure that repeats in the checkout stops the run too (`procedure.md`, Checks).
- The spec clone shows the failure when an item of the job fails in the spec clone run too. Then the CI job and the spec clone run are the two runs of `docs/ai/failures.md`, and the failure is every item that fails in both. An item that fails in the job only gets no fix now (`docs/ai/failures.md`). The next run traces it when the ci read of its head shows it again.
- Find the cause of the failure as `docs/ai/failures.md` says, and fix it. Then run the lint, and run again the check that showed the failure. That check is the failed examples, the whole suite with the seed of the job, if any, or the failed step. A whole-suite run after the fix takes the place of the spec run of the commit. After the failed examples or the failed step, the commit also runs its specs.
- Then run the other checks that the commit needs (`procedure.md`, Checks). Commit the fix in the checkout, as `docs/ai/workflows.md` Phase 3 says.
- When the failure was there before the branch (`docs/ai/failures.md` step 4), stop the run.
- When the spec clone does not show the failure, start the one rerun of the run (`procedure.md`, Checks). That is the rerun that `docs/ai/failures.md` asks for. When the jobs of the rerun pass, the failure was a flake that the spec clone does not show. Give it a DECISION row, and ci is ok. At setup, append `ci <setup HEAD> ok` to the ledger too (`procedure.md`, Checks).
- When that rerun fails again, the cause is in what the spec clone did not run. Examples are a Ruby that mise lacks, a gem or a tool that the workflow pins, and a runner of GitHub. Stop the run, and report the job, the failed examples and the run.
