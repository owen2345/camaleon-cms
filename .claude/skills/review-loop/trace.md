# Trace of a failed suite job

The review loop reads this file when a suite job of the PR head fails (`procedure.md`, Checks). The trace finds the cause of the failure in the spec clone, or in the clone of `docs/ai/failures.md` step 1. The loop finds the cause as that document says, and fixes it as `docs/ai/workflows.md` Phase 3 says.

- Several suite jobs can fail with the same examples. Then trace the one of the cell of the spec clone (its Gemfile and Ruby), else the first listed.
- Reproduce the failed job as `docs/ai/failures.md` says, in the spec clone (`procedure.md`, Checks), from its job log. The job id of `--log-failed` is the `databaseId` that the jobs command of Checks prints. First run `git -C <spec clone> clean -fdqx`: a fresh CI checkout has no ignored file and no old lock. Then sync the spec clone, before every run of the trace. The log of a job can be gone: `gh` prints `log not found`, or HTTP 410 for an expired log. Such a failure is one that the spec clone does not show (below).
- CI tests the PR merged into the base. So the sync of the trace merges the base after its `clean`: `[ -d <spec clone> ] || git clone -q <checkout> <spec clone>; git -C <spec clone> fetch -q <checkout> HEAD && git -C <spec clone> reset -q --hard FETCH_HEAD && git -C <spec clone> clean -fdq -e 'gemfiles/*.lock' && git -C <spec clone> fetch -q <checkout> refs/remotes/<base-ref> && git -C <spec clone> merge -q --no-edit FETCH_HEAD && git -C <checkout> add -A && git -C <checkout> diff HEAD --binary | git -C <spec clone> apply --allow-empty && (cd <spec clone> && bundle install --quiet)`. A conflict stops the run: report it, because the branch needs a rebase onto the base. The bisect clone of `docs/ai/failures.md` gets no merge.
- Every command of the trace in the spec clone, each sync included, starts with the cell of the job: `export BUNDLE_GEMFILE=<spec clone>/gemfiles/<rails>.gemfile MISE_RUBY_VERSION=<version> MISE_AUTO_INSTALL=0;`. `<rails>` is the gemfile name of the cell, and `<version>` the Ruby minor version of the job, both from the workflow file. Leave out a variable when the workflow file gives the job no value for it. Leave out `MISE_RUBY_VERSION` also when `mise ls --installed ruby` has no Ruby of that minor version, and say so in the report (`docs/ai/failures.md`). `MISE_AUTO_INSTALL=0` turns a wrong version into a warning, not a build. For a job with neither value, the trace runs on the Gemfile and the Ruby of the spec clone.
- The path of the gemfile is absolute (`docs/ai/failures.md`). With the export, the sync installs that gemfile, and its clean keeps the lock. The ban of `docs/ai/failures.md` on another gemfile applies to the checkout, not to the spec clone.
- For a spec step, run the failed examples first. When they pass alone, a flake is likely: start the one rerun of the run (`procedure.md`, Checks). Meanwhile, run the files of the job with its seed, as `docs/ai/failures.md` says. For a suite job of camaleon-cms, that is the whole suite, as a background task (`procedure.md`, Checks). The loop runs the whole suite only here and in the bisect of `docs/ai/failures.md` for this failure, because the CI run was one.
- For a step that is not a spec run, run that step alone in the spec clone. Examples are `bin/rubocop` and a migration. Before `bin/bundler-audit`, run `bin/bundler-audit update` once: CI reads a fresh advisory database, and the local copy can lack a new advisory. Such a step needs no second run on the same tree (`docs/ai/failures.md`). When such a step passes in the spec clone, the failure is one that the spec clone does not show (below).
- For a host app, the checkout takes the place of the spec clone in this file, without the clean and the sync (`procedure.md`, Checks). The trace reproduces only a spec step of a host-app job. Any other failed step stops the run: report it with its log.
- When the spec clone shows the failure, it is no flake: the CI job and the spec clone run are the two runs of `docs/ai/failures.md`. Find its cause as that document says, and fix it. Then run the lint, and run again what showed the failure. That is the failed examples, the whole suite with the seed of the job, or the failed step. That re-run takes the place of the spec run of the commit. Then run brakeman and zeitwerk:check, and commit the fix in the checkout, as `docs/ai/workflows.md` Phase 3 says.
- When the failure was there before the branch (`docs/ai/failures.md` step 4), stop the run.
- When the spec clone does not show the failure, the flake rule of `docs/ai/failures.md` does not apply. Start the one rerun of the run (`procedure.md`, Checks). When the jobs of the rerun pass, the failure was a flake that the spec clone does not show. Give it a DECISION row, and ci is ok. At setup, append `ci <sha> ok` to the ledger too (`procedure.md`, Checks).
- When that rerun fails again, the cause is in what the spec clone did not run. Examples are a Ruby that mise lacks, a gem or a tool that the workflow pins, and a runner of GitHub. Stop the run, and report the job, the failed examples and the run.
