# Trace of a failed suite job

The loop reads this file when a suite job of the PR head fails (`ci.md`). The trace follows `docs/ai/failures.md` "Reproduce a failed CI job" in the spec clone (`spec-runs.md`), and fixes the cause as `docs/ai/workflows.md` Phase 3 says. This file gives the inputs of that document and the outcomes of the loop.

- Of several jobs with the same failed examples, trace the one whose cell (Gemfile and Ruby) the spec clone has. Else trace the first that the jobs command of `ci.md` lists. That command also prints the job id of `--log-failed`.
- When the spec clone exists, run `git -C <spec clone> clean -fdqx` before the first sync of the trace. A fresh CI checkout has no ignored file. Sync before every run of the trace. A run that reproduces the job names the head of the failed suite run (the `<sha>` of the ci commands) as `<commit>`, and `no copy`. The run after the fix syncs with `FETCH_HEAD`, the merge and the copy.
- The merge part of the sync is `git -C <spec clone> fetch -q <checkout> refs/remotes/<base-ref> && git -C <spec clone> merge -q --no-edit <base of the job>`, with the base commit that the job log names. A log that names none gives no merge part. A conflict stops the run: the branch needs a rebase onto the base.
- Every command in the spec clone, each sync included, starts with the cell of the job from the workflow file: `export BUNDLE_GEMFILE=<spec clone>/gemfiles/<rails>.gemfile MISE_RUBY_VERSION=<version>;`. Leave out a variable that the workflow does not give the job. Leave out `MISE_RUBY_VERSION` also when the workflow names `.tool-versions` or mise lacks that Ruby (`docs/ai/failures.md`). With both left out, leave out the prefix. With the export, the sync installs that gemfile, and its clean leaves the lock, an ignored file.
- A gone log (`log not found`, or HTTP 410) is the result of its command, and the spec clone does not show that failure (below). After the rerun (below), the jobs command of `ci.md` and the log commands need `--attempt <n>` for a job of the failed attempt. `<n>` is the attempt on the `rerun` line of the suite run (`ci.md`). The ci read of the rerun and the log of a job of the rerun need no `--attempt`.
- For a spec step, run the failed examples first. When they pass alone, start the one rerun of the suite run (`ci.md`). Meanwhile run the files of the job with its seed, as a background task.
- A step that is not a spec run, such as `bin/rubocop`, runs alone in the spec clone, with no second run. When it passes there, or when it only prepares the runner, the spec clone does not show the failure (below).
- The spec clone shows the failure when an item of the job fails there too. Then the CI job and that run are the two runs of `docs/ai/failures.md`, and the failure is every item that fails in both. An item that fails in the job only gets no fix now. The next run traces it when the ci read of its head shows it again. An item that fails in the spec clone only is a flake (`docs/ai/failures.md`).
- The clone of `docs/ai/failures.md` step 1 gets no merge: check out the head of the failed suite run there. That head is `<bad>`, each command gets the cell of the job, and the suite run that failed had no fix. `<clone>` takes the place of `<spec clone>` in the cell. When the check passes there in step 3 and `git -C <spec clone> diff --quiet <head of the failed suite run> HEAD` exits with 1, the merge caused the failure. Stop the run: the branch needs a rebase onto the base.
- After the fix, run the lint and run again the check that showed the failure. That check is the failed examples, the whole suite with the seed, or the failed step. A whole-suite run takes the place of the spec run of the commit. Otherwise the commit also runs its specs. Then run the other checks (`procedure.md`, Checks) and commit as Phase 3 says. A failure that was there before the branch (`docs/ai/failures.md` step 4) stops the run.
- When the spec clone does not show the failure, start the one rerun (`ci.md`), unless the failed examples passed alone. When `ci.md` counts that rerun, stop the run when the failure shows again or the job fails in another way. When the failure shows again, its cause is in what the spec clone did not run, such as a Ruby that mise lacks. Report the job, the failed examples of both attempts and the suite run. When the job passes in that rerun and no job shows the failure again, give the flake a DECISION row. At setup, one command appends that row, then `ci <setup HEAD> <value>` with the value of the ci read after that rerun.
- A host app has no spec clone (`spec-runs.md`), so a failed suite job of a host app stops the run with its log. A failed step that only prepares the runner is the exception: the job gets the one rerun of `ci.md`, as above.
