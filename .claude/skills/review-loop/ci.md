# The ci check

The fifth check is **ci**: the GitHub workflow runs of a commit, the rows of `gh run list --commit <sha>`. Setup reads them for the `setup HEAD` (`setup.md`), and a stop that pushes for the pushed commit (`stop.md`). Each read ends with the line `ci <sha> <ok, n/a, no jobs, pending, cancelled or the failed job>` in the ledger, with the `setup HEAD` or the pushed commit as its `<sha>`. The ci field of a PASS line is the value of the last `ci` line of the run for its `<after>`, else n/a.

- The suite runs are the runs of the suite workflows of the table (`procedure.md`, Checks), the workflows that `.github/workflows/release.yml` requires in camaleon-cms. The jobs of the suite runs are the suite jobs. Every other run is advisory. A failed or cancelled one adds a note after the value of the `ci` line, `# advisory <workflow> <conclusion>`, which the STOP report repeats. A failed suite job fails ci, an advisory run never. In every command that sets `S`, `S` holds the suite workflows of the table, joined with `|` (shown with the camaleon-cms value).
- ci is n/a when the repo has no workflow file, and after a push when the pushed head carries a skip marker. A head is marked when its message (`git -C <checkout> log -1 --format=%B <sha>`) holds a bracket marker of `docs/ai/workflows.md` Phase 3, matched as a fixed string (`grep -F '<marker>'`). A head is also marked when `git -C <checkout> cat-file commit <sha> | tail -n 3 | tr '\n' '|' | grep -qE '^\|\|skip-checks: ?true\|?$'` exits with 0: a `skip-checks` line anywhere else in the message does not mark it.
- The commands take the full SHA of the head as `<sha>`: `gh` matches no short SHA. For a marked `setup HEAD`, they take the head of the newest suite run of the branch (`setup.md`, CI).
- List the runs once: `gh run list --repo <project> --commit <sha> --limit 100 --json workflowName,status,conclusion,databaseId,attempt`. When every suite workflow has a run, and every suite run is completed, read the conclusions (below). Else poll, as a background task: `for i in $(seq 120); do r=$(S='Audit|Test supported versions' gh run list --repo <project> --commit <sha> --limit 100 --json workflowName,status --jq '[.[] | select(.workflowName | test("^(" + env.S + ")$"))] | if (unique_by(.workflowName) | length) < (env.S | split("|") | length) then "absent" elif all(.status == "completed") then "completed" else "pending" end'); echo "$i $r"; case "$r" in completed) exit 0;; absent) [ "$i" -ge 11 ] && exit 3; e=0;; pending) e=0;; *) e=$((e+1)); [ "$e" -ge 3 ] && exit 5;; esac; sleep 30; done; exit 4`.
- The exit code of the poll is its result:
  - 0: every suite run is completed, so list the runs again and read the conclusions.
  - 3: a suite workflow still has no run after five minutes, so ci is `no jobs`.
  - 4: a suite run is still pending after an hour, so ci is `pending`.
  - 5: three calls of `gh` one after the other failed, and the poll has no result.
- Of the runs of one suite workflow, read the newest, with the largest `databaseId`. A conclusion `success` or `skipped` passes. For any other conclusion of a suite run, `gh run view <run id> --repo <project> --json jobs --jq '.jobs[] | select(.conclusion != "success" and .conclusion != "skipped") | "\(.databaseId) \(.conclusion) \([.steps[] | select(.conclusion == "failure")] | length) \(.name)"'` names the jobs that did not pass, with the count of their failed steps.
- A job with a failed step is a failed job, which setup traces (`trace.md`). Any other job that did not pass, or a suite run with no job, did not run to its end. It gets the one rerun of its run (below).
- Rerun a run once. Append `rerun <run id> <attempt>` to the ledger, with the `attempt` of the run in the list. Then run `gh run rerun <run id> --repo <project> --failed`, or the whole run (`gh run rerun <run id> --repo <project>`) when GitHub refuses that. After an accepted rerun, `gh run view <run id> --repo <project> --json attempt --jq .attempt` prints a number above the one on the line. Then read ci again.
- A workflow run with a `rerun` line anywhere in the ledger (`grep -a '^rerun ' <ledger>`) gets no second rerun, also from a later run of the loop. The jobs of a workflow run with a `rerun` line are the jobs of its rerun. The line counts as a rerun only when the run shows an `attempt` above the number on the line (the list and the view above). At that number the rerun command never ran or failed: run it now as the one rerun.
- A rerun whose jobs pass gives ci ok. In the rerun of the run of the `setup HEAD`, a job whose failure the trace fixed does not count (`setup.md`, CI). A job of the rerun that does not run to its end, or a refused whole-run rerun, gives ci `cancelled`. Report the run.
